# Canonical Fact Dossier — Specification

**Version:** 1.0.0
**Status:** Authoritative data contract for the per-edition factual foundation
**Last Updated:** 2026-11-10
**Integrates with:** AI Intelligence Publication Contract §4–§6, Discovery Rings Specification, Research Taxonomy v2.0, Signal Desk v1.0, Evidence Verification Pipeline

---

## 1. Purpose & Scope

The **canonical fact dossier** is the single authoritative factual foundation for
every daily AI Intelligence edition. It consolidates verified research findings,
source evidence, temporal eligibility, technical explanations, strategic
implications and unresolved uncertainty into one versioned, machine-readable
record per edition.

Every downstream representation — the Dutch technical newsletter, the
independently authored Dutch listening narrative, English website articles and
listening-text derivatives, accessible visual explanations, the technical
research audit, and source references/article metadata — must consume the same
canonical dossier. Different representations may differ in language, structure,
examples and explanation depth, but they must not introduce contradictory facts,
unsupported technical assertions or inconsistent uncertainty classifications.

### 1.1 Non-Goals (Explicit Exclusions)

This stage does **not** perform:

- ❌ Final editorial ranking or scoring
- ❌ Omission review decisions
- ❌ Article generation or publication content
- ❌ Fixed vendor quotas, arbitrary topic weights or automatic publication decisions
- ❌ Scheduled automation or website deployment
- ❌ Re-implementation of source discovery, temporal novelty decisions or claim verification

## 2. Architectural Responsibility

### 2.1 Processing Sequence

The dossier is the authoritative boundary between research and editorial
production. It consumes earlier stages; it never replaces them.

```text
Source Discovery
  → Retrieval
  → Candidate Identification
  → Temporal Classification
  → Claim Verification
  → Canonical Fact Dossier          ← this specification
  → Omission Review
  → Editorial Selection
  → Publication
```

### 2.2 Responsibility Separation

| Stage                               | Owner                                  | Output                                               |
| ----------------------------------- | -------------------------------------- | ---------------------------------------------------- |
| Source acquisition & monitoring     | Collection pipeline + Discovery Ledger | `data/discovered/*.jsonl`, `data/discovery-ledger/*` |
| Temporal novelty decisions          | `novelty-classification.ts`            | `NEW` / `CATCH_UP` / `TIME_UNVERIFIED`               |
| Claim-level evidence verification   | `evidence-verification/`               | `ClaimVerificationRecord`                            |
| **Canonical factual consolidation** | **`fact-dossier/`**                    | **`data/fact-dossiers/edition_<date>.json`**         |
| Editorial relevance assessment      | Omission review (later stage)          | Editorial readiness indicators                       |
| Final publication selection         | Editorial ranking (later stage)        | Publication records                                  |

The dossier **consumes** the results of earlier stages:

- Temporal classification is produced by `classifyNovelty` and stored verbatim.
- Claim records are consumed from `ClaimVerificationRecord` objects verbatim.
- Source metadata is consumed from the source registry and discovery ledger.
- Research domain identifiers are consumed from Research Taxonomy v2.0.

The dossier never re-decides novelty and never re-classifies evidence.

## 3. Data Contract

### 3.1 Schema

- **TypeScript schemas:** `src/lib/fact-dossier/schema.ts` (Zod)
- **JSON Schema (draft-07):** `data/schemas/canonical-fact-dossier.json` — generated from the same Zod schemas via `z.toJSONSchema`
- **Schema version:** `1.0.0` (stored on every dossier)

The TypeScript and JSON Schema contracts are generated from one source of
truth. `generateCanonicalFactDossierJsonSchema()` regenerates the JSON Schema.

### 3.2 Stable Identifiers

| Entity    | Pattern              | Source                                          |
| --------- | -------------------- | ----------------------------------------------- |
| Dossier   | `fd_[a-z0-9]{16}`    | derived deterministically from the edition date |
| Edition   | `edition_YYYY-MM-DD` | edition boundary                                |
| Candidate | `cand_[a-z0-9]{16}`  | candidate identification stage                  |
| Claim     | `claim_[a-z0-9]{16}` | evidence verification stage                     |
| Discovery | `disc_[a-z0-9]{16}`  | discovery ledger                                |
| Source    | `[a-z0-9-]+`         | source registry                                 |

Identifiers are never regenerated by the dossier. A published statement traces
back to its originating claim and evidence through these identifiers.

### 3.3 Canonical Candidate Record

For every material candidate, the dossier maintains:

- Stable candidate identifier
- Edition identifier and edition date
- Concise factual headline
- Exact statement describing what materially changed
- Research domains and discovery rings
- Organizations, products, technologies and research projects involved
- Original source identifiers and canonical URLs
- Original publication timestamp
- Earliest supported public disclosure timestamp
- Underlying event date (where applicable)
- Substantive update timestamp (where applicable)
- Applicable timezone and timestamp confidence
- Temporal eligibility status and rationale
- Previous coverage references (where available)
- Source accessibility and retrieval limitations
- Links to associated verified claims
- Unresolved questions and evidence gaps
- Processing status and audit timestamps

Unavailable metadata is recorded as an explicit gap — never inferred and never
fabricated. If no traceable publication timestamp exists, the candidate is marked
`timestampAvailability: "unavailable"` and temporal eligibility is
`TIME_UNVERIFIED`.

### 3.4 Claim-Level Consolidation

Each candidate references structured claim records containing:

- Stable claim identifier
- Precise claim statement
- Evidence classification **inherited from the verification pipeline**
- Supporting original evidence URLs
- Independent corroboration (where actually established)
- Contradictory or limiting evidence
- Relevant technical or methodological context
- Confidence and uncertainty
- Verification status and rationale
- Source provenance and verification timestamps

The dossier preserves the full distinction between:

`VERIFIED_FACT` · `VENDOR_CLAIM` · `RESEARCH_FINDING` · `ORIGINAL_REPORTING` ·
`EXPERT_INTERPRETATION` · `INFERENCE` · `SPECULATION` · `UNVERIFIED`

**A claim's inclusion in the dossier does not imply independent verification.**
Every claim carries an explicit `inclusionNote` stating its evidentiary status.
A vendor assertion, research hypothesis or consultancy forecast is never silently
converted into an established fact.

### 3.5 Technical & Scientific Context

Where relevant, the dossier preserves:

- Technical mechanisms and underlying principles
- Architecture and system behavior
- Model capabilities and limitations (demonstrated vs. announced)
- Product versions and release maturity
- Compatibility and interoperability
- Agentic workflow and software engineering implications
- Security assumptions and trust boundaries
- Evaluation methodology and benchmark conditions
- Reproducibility and independent replication
- Operational constraints, costs and availability
- Alternative explanations and counterevidence

Original technical terminology and exact values are retained when supported by
evidence. Important qualifications are never simplified away.

### 3.6 Strategic, Organizational & Economic Context

Gartner, McKinsey, Forrester, IDC, academic research and comparable strategic
intelligence sources receive the same evidentiary discipline as technical
sources. For relevant findings, the dossier preserves:

- Research objective and methodology
- Study population and sample characteristics
- Research and data collection periods
- Geographic and industry scope
- Measured outcomes and baseline
- Statistical uncertainty and methodological limitations
- Funding and potential conflicts of interest
- Enterprise AI adoption implications
- Productivity and software delivery consequences
- Economic impact, ROI and total cost of ownership
- Workforce and organizational transformation
- Governance and operational implications
- Generalizability and competing explanations

The dossier explicitly distinguishes observed results, correlations, causal
claims, market forecasts, estimates and consultancy recommendations. It does not
infer that a study applies universally to all enterprises or industries.

## 4. Temporal Eligibility & Historical Continuity

### 4.1 Inherited Novelty Classification

The dossier consumes `classifyNovelty` and stores the full
`NoveltyClassificationResult` verbatim as provenance. It then derives a
deterministic eligibility gate:

| Inherited classification  | In window?   | Repost/summary? | Eligibility gate  |
| ------------------------- | ------------ | --------------- | ----------------- |
| `NEW`                     | yes          | no              | `NEW_PASS`        |
| `NEW` / `TIME_UNVERIFIED` | yes          | yes             | `NEW_FAIL`        |
| `CATCH_UP`                | no           | —               | `CATCH_UP`        |
| `TIME_UNVERIFIED`         | no / unknown | —               | `TIME_UNVERIFIED` |

This mapping is a deterministic derivation, not an independent novelty decision.

### 4.2 Edition Boundary

The exact editorial window is **05:00 Europe/Amsterdam** on the previous calendar
day (inclusive) to 05:00 Europe/Amsterdam on the edition date (exclusive), with
correct DST handling (23h spring-forward, 25h fall-back). The window is fixed by
the edition date and never by execution time.

### 4.3 Timestamp Distinctions

The dossier keeps four timestamp families strictly separate:

- **Original publication timestamp** — when the source published the item
- **First public disclosure timestamp** — when the information first became public
- **Underlying event date** — when the actual event occurred
- **Substantive update timestamp** — when prior reporting was materially updated

New disclosures about older events are supported: a item published inside the
window about a 2023 event is `NEW_PASS`, while its `underlyingEventDate` remains 2023.

### 4.4 Historical Continuity

- Actually available earlier editions are referenced through `previousCoverage`.
- Missing historical publications remain an explicit uncertainty. They are
  **never** interpreted as proof of no previous coverage.
- Each candidate records `checkedEditionDates`, `missingEditions` and a note.

## 5. Editorial Readiness (Descriptive Only)

The dossier prepares structured information for the subsequent omission review
and editorial ranking stages. It computes **descriptive, evidence-backed
indicators** for:

- Material novelty
- Technical or scientific significance
- Real-world consequences
- Enterprise and economic implications
- Generalizability
- Strength and limitations of evidence
- Practical engineering relevance
- Availability and maturity
- Potential overlap with other candidates

Every indicator carries:

- `level`: `high` | `medium` | `low` | `unclear`
- `evidence`: human-readable, evidence-backed reasons
- `traceableTo`: stable identifiers (candidate, claim, source, `novelty-classification`)

The dossier **does not** introduce fixed vendor quotas, arbitrary topic weights,
automatic publication decisions, or final editorial ranking. Strategically
important developments are evaluated alongside technical breakthroughs. Personal
relevance to GitHub Copilot, VS Code or agentic engineering does not override the
independent assessment.

## 6. Storage, Schemas & Versioning

### 6.1 One Authoritative Dossier Per Edition

```text
data/fact-dossiers/edition_<YYYY-MM-DD>.json
```

### 6.2 Guarantees

| Guarantee                           | Implementation                                                                          |
| ----------------------------------- | --------------------------------------------------------------------------------------- |
| Stable candidate/claim references   | Identifiers consumed from earlier stages; never regenerated                             |
| Deterministic serialization         | Recursive key sorting (`canonicalPrettyJson`)                                           |
| Explicit schema version             | `schemaVersion: "1.0.0"` on every record                                                |
| Idempotent updates                  | Identical content ⇒ no write; changed content ⇒ new version with `previousVersionHash`  |
| Atomic writes                       | Temp file + `rename`                                                                    |
| Preservation of historical evidence | Content hash chain via `previousVersionHash`                                            |
| Readback verification               | Byte equality + recomputed content hash after write                                     |
| Backward-compatible evolution       | New fields optional; `schemaVersion` gates migrations                                   |
| Resumable processing                | Per-candidate failures recorded in `processingAudit`; a later run retries only failures |
| No uncontrolled duplication         | Claims/sources are referenced by identifier, not copied                                 |
| No mandatory cloud database         | Local filesystem only                                                                   |

### 6.3 Content Hash

`contentHash = sha256(canonicalJson(dossier without contentHash and previousVersionHash))`

The hash identifies the factual state of the edition, independent of its position
in a version chain.

### 6.4 Status Lifecycle

`draft` → `consolidating` → `ready-for-omission-review` → `complete`
`partial` (some candidates failed) · `failed` (nothing could be consolidated)

## 7. Validation & Invariants

`validateFactDossier(dossier)` enforces:

- Zod schema validation (structure, enums, identifier patterns)
- Unique candidate and claim identifiers
- Source-to-claim traceability (every claim references its candidate)
- Preservation of original evidence URLs
- Publication / disclosure / event / update timestamp distinctions
- Accurate inheritance of novelty classifications
- Preservation of evidence classifications
- **Prevention of unsupported factual promotion**:
  - `VENDOR_CLAIM` / `INFERENCE` / `SPECULATION` / `UNVERIFIED` must remain `L0`
    and must not be marked `verified` / `partially-verified`
  - `verified` status requires `VERIFIED_FACT`, `RESEARCH_FINDING` or
    `ORIGINAL_REPORTING`
  - Inclusion notes must not promote unverified classifications
- Editorial readiness traceability (all `traceableTo` references resolve)
- Edition summary consistency
- Content hash integrity
- Canonical serialization round-trip stability

## 8. Downstream Interface

Downstream stages consume the dossier through:

1. **The persisted JSON** at `data/fact-dossiers/edition_<date>.json`.
2. **The TypeScript API** in `src/lib/fact-dossier/index.ts`:
   - `FactDossierStore.load(editionDate)` / `loadAndValidate(editionDate)`
   - `validateFactDossier(dossier)`
   - `buildDossier(editionDate, inputs, context)`
3. **The JSON Schema** for independent validators.

A downstream consumer must:

- Resolve candidate and claim identifiers before use.
- Carry the evidence classification and uncertainty into the representation.
- Never present a `VENDOR_CLAIM`, `INFERENCE`, `SPECULATION` or `UNVERIFIED`
  statement as an established fact.
- Preserve the distinction between publication, first disclosure, underlying
  event and retrieval timestamps.
- Keep the dossier's uncertainty classifications consistent across representations.

## 9. Cost & Execution Constraints

- Deterministic TypeScript + Node.js tooling with **pnpm**.
- Free NVIDIA Nemotron via OpenRouter is the primary inference route; Nous Portal
  Free Tier is the configured fallback, both through the existing
  `FreeLLMClient` (hard-coded $0 cost budget).
- Model reasoning is used **only** for genuine semantic analysis (optional
  exact-statement enrichment). It is never required to complete a dossier.
- If model capacity is unavailable, completed verified records are preserved and
  unfinished work is marked explicitly (`enrichment.status: "unavailable"`).
- Missing analysis is **never manufactured** to complete a dossier.
- No paid inference, no additional paid services, no unnecessary infrastructure.

## 10. CLI

```bash
# Build from the repository's candidate/discovery/verification data
pnpm build:dossier -- --edition 2025-01-15

# Build a clearly-labeled synthetic demonstration dossier (test fixtures)
pnpm build:dossier:demo -- --edition 2025-01-15

# Optional model-assisted enrichment (free providers only)
pnpm exec tsx scripts/build-fact-dossier.ts --edition 2025-01-15 --enrich

# Validate persisted dossiers
pnpm validate:dossier
pnpm validate:dossier data/fact-dossiers/edition_2025-01-15.json

# Validate all editorial data files against their JSON schemas
pnpm validate:data
```

> **Synthetic data notice:** `--demo` uses invented test fixtures and is clearly
> labeled. It must not be presented as actual research findings.

## 12. Known Integration Gaps

- The repository's seeded `data/candidates/2025-01-15.jsonl` records predate the
  Research Taxonomy v2.0 / Signal Desk extensions and lack
  `ringClassificationDistribution` and `researchDomains`. They cannot be
  consolidated without triage enrichment; the dossier records these as explicit
  per-candidate failures rather than inferring rings or domains.
- No verified claim records are persisted under `data/evidence-verification/` in
  the repository, so the CLI's real-data build currently produces candidates
  with zero claims and explicit evidence gaps.
- The omission review, editorial ranking, article generation, scheduled
  automation and website deployment stages are intentionally **not** implemented.
